# DOC-001: Use `doc` ItemType for Architecture Decision Records

## Status

Accepted

## Date

2026-04-04

## Context and Problem Statement

GitHub Copilot agents increasingly create "decision" items during development sessions.
DevSteps currently has no structured path for Architecture Decision Records (ADRs).
Should DevSteps add `adr` as a new ItemType, or use the existing `doc` type?

Key constraints discovered during SPIKE-046 research:
- ItemType enum changes are a BREAKING CHANGE (new prefix, new directory, schema migration)
- ADR lifecycle (proposed → accepted → deprecated → superseded) does not match the item lifecycle (draft → planned → in-progress → review → done)
- 18+ external sources and 6 internal codebase analyses consistently reject a separate ADR type

## Decision Drivers

- ADRs need their own lifecycle states, not the standard item status flow
- The `doc` type was already present in the Zod schema but not activated in config
- Adding a new ItemType requires migration tooling, index updates, and prefix allocation
- Industry best practice (MADR, adr-tools, Spotify, AWS) stores ADRs as documents, not work items
- The `documents`/`documented-by` relationship type already exists in the schema as a flexible (non-hierarchical) relation

## Considered Options

| Option | Description | Pros | Cons |
|--------|------------|------|------|
| Path A: New `adr` ItemType | Add `adr` to ItemType enum with custom lifecycle | Native first-class support | Breaking change, lifecycle mismatch, 2 blockers (custom lifecycle engine + migration tooling) |
| Path B: Knowledge subsystem | Separate `.devsteps/knowledge/` storage (STORY-145) | Clean separation, proper lifecycle | Requires new subsystem, parallel to items, high effort |
| Path C: `doc` type activation | Activate existing `doc` ItemType, use MADR templates | Zero schema changes, immediate, uses existing infrastructure | ADR lifecycle not enforced by system (metadata-level only) |

## Decision Outcome

Chosen option: **Path C — activate `doc` ItemType**, because it requires zero breaking changes,
leverages existing infrastructure (Zod schema, flexible relationships, config system),
and provides immediate value. Path B remains the long-term evolution target.

The activation sequence was: fix config desync (BUG-076) → derive enums from Zod (BUG-077/TASK-374) →
add CLI shortcut (BUG-078) → freeze tests (TASK-411) → validation guards (STORY-239).

### Positive Consequences

- ADRs can be created immediately via `devsteps add doc "ADR-NNN: title" --tags adr`
- MADR 4.0 template auto-populates for ADR-tagged doc items (TASK-413)
- No schema migration needed — `doc` was already in the Zod enum
- `documents`/`documented-by` relations link ADRs to the items they govern
- Freeze tests prevent future enum desync (TASK-411)

### Negative Consequences

- ADR lifecycle (proposed/accepted/deprecated/superseded) is not enforced at the system level — stored in description metadata only
- Mitigation: Future `metadata.adr_status` field or Path B knowledge subsystem
- `doc` type is generic — not all docs are ADRs
- Mitigation: `adr` tag + `isMadrCandidate()` heuristic distinguishes ADRs from other docs
