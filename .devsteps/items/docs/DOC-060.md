# ADR: BM25 over Vector Embeddings for Knowledge-OS Retrieval

## Status
Accepted (EPIC-046 planning session)

## Context
The CCMS Phase 2 proposal includes semantic embeddings + clustering to auto-assign fragment components.
DevSteps targets knowledge bases of up to ~1,000 doc items. Two retrieval approaches were evaluated.

## Decision
Use **BM25 lexical retrieval** at current scale. No vector embedding infrastructure will be added
until the corpus exceeds 1,000 items AND the 2% recall gap becomes a user-visible problem.

## Rationale
| Factor | BM25 | Vector DB |
|--------|------|-----------|
| Infrastructure | zero (pure TypeScript) | Docker/service required |
| Recall gap | baseline | +2% at <1000 items |
| Index rebuild | ~50ms | minutes (embedding API calls) |
| Offline operation | yes | requires embedding API |
| API cost | zero | token cost per re-embedding |
| Debuggability | transparent (tf-idf logs) | opaque (cosine similarity) |

## Trigger threshold for re-evaluation
- Corpus > 1,000 doc items AND
- User reports ≥3 specific recall failures per month

## Component auto-assignment alternative (replaces Phase 2 embedding)
Use tag-based component assignment (`component:` structured tag or first-class field via STORY-290).
Authors assign component deliberately or semi-automatically via `devsteps_suggest_bom_location` (tag-matching v1).

## Consequences
- Phase 2 (semantic clustering) is NOT implemented
- Component metadata assigned by author or by tag-matching heuristic, not by AI clustering
- Future path: if threshold triggered, add embedding as optional async enrichment pass, NOT core query path
