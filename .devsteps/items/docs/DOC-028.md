## Doc Item — Content Fragment in the DevSteps Documentation Graph

A `doc` item is a **Content Fragment**: one section of a documentation document, bidirectionally linked to backlog items. Copilot can derive requirements and tasks from the fragment content (`doc → items`), and can navigate from any backlog item back to its documentation context (`items → doc`).

**Document structure:** H1 = Diataxis type (tutorial, reference, how-to, explanation) · H2 = chapter · H3 = section · H4 = subsection/function-level. Each heading level is a separate `doc` item and a separate BOM node. Copilot navigates **upward** in the BOM tree for overview, **downward** for implementation details.

Unlike `story` or `task`, `doc` is **cross-cutting** — it sits outside the Epic→Story→Task hierarchy and spans it via `documents` / `documented-by` relations. A `doc` item introduces a parallel description layer: the same functionality can be documented at multiple resolutions, each as an independent fragment.

### Was ein doc-Item enthält

| Feld | Bedeutung |
|------|-----------|
| `title` | Abschnitts- oder Dokumenttitel |
| `description` | Der eigentliche Markdown-Inhalt des Abschnitts |
| `affected_paths` | Pfad zur `.md`-Datei (z.B. `docs/reference/overview.md`) |
| `tags` | Heading-Level (`h1`, `h2`, `h3`), Diataxis-Typ, thematische Tags |
| `linked_items.documents` | Items die dieses Doc-Item dokumentiert |
| `linked_items.documented-by` | Andere Doc-Items die dieses belegen |

### Diataxis-Klassifikation

Jedes doc-Item gehört zu einem Diataxis-Typ (gesetzt via `tags` oder `metadata`):

| Typ | Zweck |
|-----|-------|
| `tutorial` | Lernorientiertes Schritt-für-Schritt |
| `how-to` | Zielorientiere Anleitung für bekannte Aufgabe |
| `reference` | Informationsorientiertes Nachschlagewerk |
| `explanation` | Verständnisorientiertes Hintergrundwissen |
| `architecture` | ADR, Architektur-Entscheide |
| `research` | Spike-Ergebnisse, Evaluationen |

### Inhalt schreiben

Der Inhalt eines doc-Items wird über das `update`-Tool ins `description`-Feld geschrieben — als vollständiges Markdown mit Überschriften, Listen, Tabellen und Code-Blöcken.

> **Kein separates `write_content`-Tool nötig** — das vorhandene `update`-Tool ist ausreichend.

### BOM-Verknüpfung

Das doc-Item kann via `doc_id`-Feld in `docs-map.json` mit einem ARCH-NNN-Knoten verknüpft sein. Damit wird es Teil des strukturierten Dokument-Baums (BOM).

> Das doc-Item und der ARCH-Knoten sind unabhängig — das doc-Item lebt im Backlog, der ARCH-Knoten in der BOM-Manifest-Datei. Beide zeigen aufeinander (`doc_id`), aber keiner ist dem anderen untergeordnet.

### Bidirektionale Navigation

```
doc → items:  DOC-028 --[documents]--> STORY-042, TASK-117
items → doc:  STORY-042.linked_items['documented-by'] = ['DOC-028']
BOM aufwärts: ARCH-003.parent_id → ARCH-001 (Kapitelübersicht)
BOM abwärts:  ARCH-003.devsteps_items = ['DOC-028', 'STORY-042']
```

> **Hinweis:** Die items→doc Synthese (Backlog → gerenderte Markdown-Datei) ist als `devsteps_docs_assemble`-Handler geplant (STORY-250) aber noch nicht implementiert. Die Datenstruktur für beide Richtungen ist vollständig vorhanden.
