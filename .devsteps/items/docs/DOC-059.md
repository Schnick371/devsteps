## Content Fragment Hierarchy — H-Level Mapping and Structure Rules

A `doc` item is a **Content Fragment**: one autonomous section of a documentation document. Each fragment captures everything under **one H1 heading** in the authored markdown — internal H2/H3/H4 sub-headings are content-within, not separate items.

---

### Authoring Invariant

> **Always author doc-item descriptions starting with `# Title` (H1).**  
> The assembler computes `offset = bom_level − 1` and shifts all headings at export time. Hard cap: H6.

---

### BOM Granularity (fixed)

| BOM level | Role | Authoring level | Output level |
|-----------|------|-----------------|-------------|
| 1 | **Document root** — one per Diataxis type per output file | H1 | H1 |
| 2 | **Chapter fragment** — major section of the document | H1 (→ H2 at assembly) | H2 |
| 3 | **Section fragment** — concrete topic or command | H1 (→ H3 at assembly) | H3 |
| 4 | **Subsection fragment** (optional) — narrow sub-topic | H1 (→ H4 at assembly) | H4 |

**One doc-item = one H1 block.** H2–H5 sub-headings WITHIN the description are content structure inside that fragment, NOT separate doc items. If a sub-topic warrants its own backlog tracking, it becomes a new doc item at BOM level +1 with its own H1.

> **Previous model (deprecated):** The old schema assigned each heading level (H1–H5) to a separate doc item. That model was too fine-grained — a 7-section document would produce 9+ items, far below optimal RAG chunk size (300–1500 tokens). The H1-block model was adopted in STORY-267 (April 2026).

---

### Backlog Linkage (free, not fixed)

Any BOM-level fragment may link to any backlog item type (`epic`, `story`, `task`, `bug`, `spike`, `test`). No hard schema enforces which BOM level must link to which item type.

**Practical convention (not enforced):**
- BOM level 1–2 → typically linked to `epic` or `story` (broad scope)
- BOM level 3–4 → typically linked to `task` or `bug` (concrete implementation detail)

---

### Revised Example: Reference Document for CLI Commands

```
DOC-002 (BOM level 1: reference root — H1 in output)
  DOC-010 (BOM level 2: chapter — Core Commands — H2 in output)
    DOC-020 (BOM level 3: section — devsteps add — H3 in output)
    DOC-021 (BOM level 3: section — devsteps update — H3 in output)
  DOC-011 (BOM level 2: chapter — MCP Tools — H2 in output)
```

DOC-020 `description` begins with `# devsteps add` (H1) and contains:
```markdown
# devsteps add

Adds a new work item to the backlog.

## Usage

```bash
devsteps add --type story --title "My Story"
```

## Options

| Flag | Description |
|------|-------------|
| `--type` | Item type (story, task, bug, …) |
```

H2/H3 inside DOC-020 are **prose content**, not separate doc items.

### Assembly

The BOM tree (`docs-map.json`) defines the assembly order. `devsteps_docs_assemble` (TASK-437 — exportHandler) renders the tree into a single Markdown file:  
1. For each node at BOM depth D: `offset = D − 1`
2. Apply `adjustHeadingLevels(fragment.description, offset)` (TASK-436)
3. Strip YAML frontmatter from each fragment
4. Concatenate in BOM order
