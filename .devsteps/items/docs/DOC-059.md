## Content Fragment Hierarchy — H-Level Mapping and Structure Rules

A `doc` item is a **Content Fragment**: one autonomous section of a documentation document. Each fragment has exactly one heading level (H1–H5), one Diataxis type, and links to zero or more backlog items.

---

### H-Level Schema (fixed)

| H-Level | Role | Detail depth |
|---------|------|-------------|
| H1 | **Diataxis type root** — `tutorial` · `how-to` · `reference` · `explanation` · `architecture` · `research` | Outline only; no H0 above |
| H2 | **Chapter** — A major section within the Diataxis type | Overview-level prose |
| H3 | **Section** — A topic within a chapter | Implementation-relevant detail |
| H4 | **Subsection / Function** — A concrete function, command, or step | Full detail; Tasks and Bugs linkable here |
| H5 | **Detail** — Edge cases, variations, footnotes | Very specific; rarely needs backlog links |

> H1 is always the root of the document tree for that Diataxis type. There is no super-H1 above it. A fragment cannot be H0.

---

### Backlog Linkage (free, not fixed)

Any H-level fragment may link to any backlog item type (`epic`, `story`, `task`, `bug`, `spike`, `test`). No hard schema enforces which H-level must link to which item type.

**Practical convention (not enforced):**
- H1–H2 → typically linked to `epic` or `story` (broad scope)
- H3–H4 → typically linked to `task` or `bug` (concrete implementation detail)
- H5 → linked to `task` or `bug` if at all

---

### One Fragment = One Heading

Each `doc` item corresponds to exactly one heading and its immediate content block — NOT a nested subtree. If a subtree is needed, each sub-heading is its own separate `doc` item with a BOM parent–child relationship.

**Example: reference document for CLI commands**

```
DOC-002 (H1: reference)
  DOC-010 (H2: chapter — Core Commands)
    DOC-020 (H3: section — devsteps add)
      DOC-030 (H4: subsection — --type flag) → linked to TASK-042
      DOC-031 (H4: subsection — --eisenhower flag) → linked to TASK-043
    DOC-021 (H3: section — devsteps update)
  DOC-011 (H2: chapter — MCP Tools)
```

The BOM adjacency list (`docs-map.json`) stores this tree via `parent_id`. Assembly (`devsteps_docs_assemble`) renders it in order.

---

### Content Depth by Level

The CONTENT of a fragment becomes more detailed as H-level increases — driven by what is needed, not by a style rule. Diataxis type determines the writing style (instructional / descriptive / narrative); H-level determines the scope and specificity of content.

| Diataxis type + H-level | Typical content |
|------------------------|----------------|
| `tutorial` H2 | Learning goal for the chapter |
| `tutorial` H3 | Step the learner performs |
| `reference` H2 | Overview of a command group |
| `reference` H3 | One command: signature, options, return |
| `reference` H4 | One flag or parameter: constraints, examples |
| `explanation` H2 | Why a design decision was made |
| `explanation` H3 | Trade-off analysis, alternatives considered |

---

### Assembly

The BOM tree (`docs-map.json`) defines the assembly order. `devsteps_docs_assemble` (planned — STORY-250) renders the tree into a single Markdown file by concatenating fragments in BOM order, stripping YAML frontmatter from each fragment before concatenation.
