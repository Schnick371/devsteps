## ARCH-NNN Schema — Vollständige Feldbeschreibung

Jeder Knoten in `docs-map.json` ist ein `DocsMapNode`-Objekt (TypeScript-Typ in `packages/shared/src/types/docs-map.ts`).

| Feld | Typ | Pflicht | Beschreibung |
|------|-----|---------|--------------|
| `id` | `string` | ✅ | Stabiler BOM-Schlüssel, Format `ARCH-NNN`. **Kein DevSteps ItemType** — wird nie in `generateItemId()` registriert (ADR-S2-12) |
| `doc_id` | `string?` | — | `DOC-NNN` Item das diesen Abschnitt besitzt |
| `parent_id` | `string\|null` | ✅ | `ARCH-NNN` des Elternknotens, oder `null` für Root-Knoten (L0) |
| `order` | `number` | ✅ | Sortierposition unter Geschwisterknoten. Gap-Nummerierung empfohlen: 10, 20, 30 |
| `title` | `string` | ✅ | Abschnittsüberschrift (spiegelt H1–H4 im MD-Inhalt) |
| `description` | `string?` | — | Redaktionelle Notiz. Beim Root-Knoten (L0): `diataxis_type + language + Abstract` |
| `devsteps_items` | `string[]` | ✅ | Work-Item-IDs (beliebiger Typ) die diesen Abschnitt belegen oder dokumentieren |
| `tsd_heading_depth_max` | `1\|2\|3\|4?` | — | Maximale Heading-Tiefe bei der Rendering in diesem Teilbaum (überschreibt globalen Slider) |
| `default_depth` | `1\|2\|3\|4?` | — | Standard-Zoom-Ebene bei VS Code Depth View (nur Präsentations-Hint) |

### Root-ARCH-NNN Konvention

Der Wurzelknoten (`parent_id: null`) repräsentiert das **Gesamt-Dokument**:

```json
{
  "id": "ARCH-001",
  "doc_id": "DOC-NNN",
  "parent_id": null,
  "order": 10,
  "title": "Dokument-Titel",
  "description": "diataxis_type: reference | language: de | Abstract des Dokuments",
  "devsteps_items": []
}
```

Das `doc_id`-Feld zeigt auf ein DOC-Item das Titel und Abstract trägt. Dieses DOC-Item soll **kein Kapitel** sein — sein Inhalt beschreibt das Dokument selbst.

### Warum kein eigener ItemType für den Root-Knoten?

Ein neuer ItemType (`publication`, `manifest`, `docmap`) wurde evaluiert (**Research: 2026-04-09**) und abgelehnt:

- **ADR-S2-12** (ADOPTED): ARCH-NNN sind manifest-only — keine Lifecycle-Entitäten
- **SSOT-Konflikt**: parallele Datenhaltung in Item + `docs-map.json` → chronisches Drift-Risiko
- **Change-Impact**: 8–10 Pflichtstellen in 4 Packages, `enum-sync.test.ts` bricht by-design ab
- **Kein Industrie-Präzedenz** in Task-Tracking-Systemen

**Alternative:** Root-ARCH-NNN mit `doc_id`-Brücke zu einem gewöhnlichen DOC-Item ist ausreichend und ADR-konform.
